# EF Core Standards

Entity and schema configuration for EF Core. Referenced by [dotnet-api-standards](../SKILL.md).

Declare schema with data attributes. Reach for the Fluent API only for what no attribute can express.

## Entity identity

A primary key is named for its entity — `EmployeeId` on `Employee`, never a bare `Id`. The property, the column, and every foreign key referencing it carry that one name, so `Employee.EmployeeId` and `TimeEntry.EmployeeId` read as the same key and a joined result set has no colliding `Id` columns. EF Core treats `<TypeName>Id` as the key by convention; `[Key]` still declares it explicitly.

The DTO the repository returns carries the same name, so Mapster maps it by convention with no member configuration.

The database provider generates every key value. Application code never assigns one.

- Key properties are store-generated — `[DatabaseGenerated(DatabaseGeneratedOption.Identity)]`, which EF Core already infers for a simple integer key.
- A `Guid` key is generated by the database too, via a default value constraint (`NEWSEQUENTIALID()` on SQL Server). Never `Guid.NewGuid()` in a constructor, service, or mapper — client-generated keys defeat the database's uniqueness guarantee and fragment the clustered index.
- A key property has no setter reachable from application code, and no request model or DTO-to-entity map ever populates one.

## Base entities

Fields shared across entities live on an `abstract` base entity. Separate a field into a base as soon as a second entity needs it *for the same reason* — not after it has been copy-pasted. Two entities whose `ExpiresAt` means different things do not share a concern.

**One base per concern**, named for that concern — `BaseChangeTrackingEntity`, not `BaseEntity`. A name saying only "base" states no boundary, so the next author has nowhere else to put an unrelated field, and every column the base accumulates becomes a column on every table inheriting it.

| Base | Carries | Applies to |
|---|---|---|
| `BaseChangeTrackingEntity` | `CreatedAt`, `CreatedBy`, `ModifiedAt`, `ModifiedBy` | every persisted entity |
| `BaseSoftDeleteEntity` | `IsDeleted`, `DeletedAt`, `DeletedBy` | entities that are never hard-deleted |
| `BaseTenantEntity` | `TenantId` | entities partitioned by tenant |

The key is never one of them — its name varies per entity, so each entity declares its own.

**Inherit only the columns something writes.** `BaseChangeTrackingEntity` above is the four-column form, and it is the right floor once all four have writers — `CreatedBy` and `ModifiedBy` need an identity, so they presuppose authentication, and `ModifiedAt` presupposes an endpoint that updates. Until then the floor is the narrower `BaseCreationStampedEntity`, carrying `CreatedAt` alone. That is conformance, not an exception: inheriting a column nothing populates is the schema defect the next section names. Widening later is `BaseChangeTrackingEntity : BaseCreationStampedEntity` — an addition, not an edit.

Each base declares a marker interface. Global query filters and `SaveChanges` interceptors target the interface, so cross-cutting behavior never enumerates entity types and a new entity picks it up by inheriting.

```csharp
public interface IChangeTracked
{
    DateTimeOffset CreatedAt { get; set; }
    string CreatedBy { get; set; }
    DateTimeOffset? ModifiedAt { get; set; }
    string? ModifiedBy { get; set; }
}

public abstract class BaseChangeTrackingEntity : IChangeTracked
{
    public DateTimeOffset CreatedAt { get; set; }
    public string CreatedBy { get; set; } = string.Empty;
    public DateTimeOffset? ModifiedAt { get; set; }
    public string? ModifiedBy { get; set; }
}

public abstract class BaseTenantEntity : BaseChangeTrackingEntity, ITenantScoped
{
    public int TenantId { get; set; }
}

[Table("Employees")]
public class Employee : BaseTenantEntity
{
    [Key]
    public int EmployeeId { get; private set; }
}
```

### Composing them

C# gives an entity one base class, so order the chain from the most universal concern to the narrowest, and inherit only where the narrower concern *always* implies the wider one — a tenant-partitioned row is always change-tracked, so `BaseTenantEntity : BaseChangeTrackingEntity` holds. Never extend the chain for convenience: an entity that inherits a column it should not have is a schema defect, not a tidy-up.

When two concerns are genuinely independent and collide on one entity, keep the more widely used one in the chain and declare the other's properties on the entity itself, implementing that concern's interface so the filters and interceptors still find it.

Split an existing base the moment an entity inheriting it needs only some of its columns — that base is carrying two concerns.

Every base is `abstract` and has no `DbSet`, so EF Core maps its properties into each derived entity's own table rather than creating an inheritance hierarchy.

## Repository boundary

The boundary is directional: **an entity flows into a repository, never out of one.**

| Direction | Repository signature | Who constructs the entity |
|---|---|---|
| Read | Returns a DTO — `EmployeeDto`. Never an entity, never an `IQueryable` | Nothing does; the query projects straight to the DTO |
| Write | Accepts an entity, returns a DTO | The service, before it calls the repository |

**Reads.** Project in the query — `ProjectToType<EmployeeDto>(config)` — so EF Core translates the map to SQL, the database returns only the columns the DTO declares, and no entity is materialized. Enumerate inside the repository so the caller cannot extend or defer the query. Pass the config explicitly: a config-less `ProjectToType<TDto>()` resolves against static `TypeAdapterConfig.GlobalSettings` and, because Mapster matches by convention, returns a plausible DTO while bypassing every registration.

**Writes.** The service maps its input to the entity with the generated mapper and passes the entity to the repository, which adds and saves. The repository still returns a DTO: store-generated values — the key, a timestamp written by an interceptor — are knowable only after `SaveChanges`.

**Mapping stays in a dedicated mapper file either way, but not the same kind of file.** The read direction must be a runtime `TypeAdapterConfig` registration, because only that can be projected into SQL; the request-to-entity direction must be the Mapster source generator, because only that makes `required` compiler-enforced. Neither mechanism substitutes for the other. A service *calls* a mapper; it never contains a mapping expression. Full table: [SKILL.md](../SKILL.md) → **Data Mapping**.

**What this protects.** No materialized or tracked entity escapes a repository, so lazy loading cannot fire after the `DbContext` is disposed, no database column set reaches a response, and a controller stays two layers from the schema. The accepted cost is that a service names the entity in order to construct one, so a column rename reaches the service and stops there.

Entity types therefore appear in five places only: the repository **and its interface** — the write member declares the entity parameter on both — the `DbContext`, entity configuration, and the mapper that constructs them. Inside a service they appear in method bodies, never in a member signature.

## Schema attributes

| Concern | Attribute |
|---|---|
| Table name | `[Table("Employees")]` |
| Column name, type, or order | `[Column]` |
| Primary key | `[Key]` on the `<Entity>Id` property, or `[PrimaryKey]` on the class for a composite key |
| Required column | `[Required]` |
| String length | `[MaxLength]` |
| Decimal precision and scale | `[Precision]` |
| Index, unique index | `[Index(nameof(Email), IsUnique = true)]` on the class |
| Foreign key | `[ForeignKey(nameof(DepartmentId))]` |
| Navigation pairing | `[InverseProperty]` |
| Cascade behavior | `[DeleteBehavior]` |
| Excluded property | `[NotMapped]` |
| Concurrency token | `[Timestamp]`, `[ConcurrencyCheck]` |
| Store-generated value | `[DatabaseGenerated]` |

`[Required]` declares validation and schema only. It does not satisfy the compiler's nullable-reference analysis, so a non-nullable reference property still needs the `required` modifier or an initializer — otherwise the build fails with `CS8618` wherever warnings are errors.

## Fluent API

Use only for configuration with no attribute equivalent:

| Fluent-only configuration |
|---|
| Value converters and value comparers |
| Default and computed column values |
| Global query filters |
| Alternate keys, composite foreign keys, check constraints |
| Filtered indexes |
| Owned type, complex type, and inheritance mapping |
| Seed data |

One `IEntityTypeConfiguration<T>` per entity, each in its own file. An entity needing no fluent configuration gets no file.

## Guardrails

- `OnModelCreating` contains only the assembly scan that applies entity configurations.
- Every `IEntityTypeConfiguration<T>` file contains at least one call with no data-attribute equivalent.
- No mapping expression appears in a `DbContext`.
- Every key property is named `<EntityName>Id`; no entity, DTO, or column is named a bare `Id`.
- No assignment to a primary key property appears outside a migration or test fixture, and no `Guid.NewGuid()` produces one.
- Every base entity is `abstract`, named `Base<Concern>Entity`, has no `DbSet`, and declares one concern's properties behind that concern's interface.
- Every entity inherits a creation-stamp base — `BaseCreationStampedEntity`, or `BaseChangeTrackingEntity` once all four of its columns have writers — directly or through a narrower base, needs every column it inherits, and redeclares none of them.
- Every global query filter and `SaveChanges` interceptor targets a concern interface, never a list of entity types.
- No repository member returns an entity type, and no `IQueryable` crosses a repository boundary.
- A repository write member may accept an entity; every repository member returns a DTO or a primitive.
- No controller references the entity namespace.
- No service or controller member signature names an entity type.
- Entity types are named only by the repository and its interface, the `DbContext`, entity configuration, the mapper that constructs them, and service method bodies.
- The request-to-entity map is a generated mapper; the read map is a projection carrying its config. Neither is hand-written and neither is swapped for the other.
